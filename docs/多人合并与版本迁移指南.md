# 多人合并与版本迁移指南

本指南说明如何用网页翻译编辑器**安全合并别人的译文**，以及游戏更新后如何
**把旧版本翻译迁移到新版本**。两条流程都以“默认只填空白、绝不静默覆盖”为前提。

## 一、合并别人的译文（交接）

### 前提

你和对方处理的是**同一批 Kit**：`unitId`、`protectedSource`、占位符与各身份
字段都完全一致，只是译文不同。编辑器会在合并前校验这些字段，任何一条不一致都会
整体拒绝，当前工作不会被改动。

### 四种合并方式

在“导入已有译文 ZIP / JSONL”旁的下拉框选择：

1. **只填空白（推荐，默认）**：只补充当前空白的译文；与已有译文冲突的条目跳过。
2. **保留当前译文，跳过冲突**：同样只填空白，并把跳过的冲突列在“冲突”面板里
   供你查看。
3. **预览冲突后逐条选择**：打开冲突面板，逐条查看“原文 / 当前译文 / 导入译文”，
   对每条选择“保留当前”或“采用导入”，也可整批采用或整批保留，确认后应用。
4. **覆盖不同译文（需确认）**：在明确确认后，用导入译文覆盖冲突条目。
   **不会**把它作为默认选项。

### 合并前预览统计

导入前会给出：可直接补充数量、内容一致数量、冲突数量、无法匹配数量、结构异常
数量。合并完成后给出结果摘要，且**整次合并作为一组操作，可以撤销**。

### 匹配规则

只使用稳定 `unitId`，并校验原文、占位符与身份字段；**不会**用数组下标、
当前显示顺序、当前页码或单纯文本相似度来匹配。

## 二、把旧版本翻译迁移到新版本

### 使用场景

游戏更新后，旧版本已有一批翻译。新旧版本的条目会有增、删、改，你希望尽量复用
未变化的译文，并单独处理真正需要重做的内容。

### 操作流程

1. 先用 Toolkit 导出**新版本** Kit，并在编辑器中打开它。
2. 点“迁移新版本译文”，选择**旧版本**翻译文件：
   已翻译的 Kit ZIP、`segments.jsonl`，或编辑工程 `*.dolpkit.json`。
3. 编辑器按稳定 ID 与保护后原文分析差异，打开迁移面板。
4. 查看分类数量，点“执行迁移（仅填充空白）”。
5. 如需一并采用“原文相同但 ID 不同”的建议，会在确认后一并填入空白条目。
6. 迁移结果可撤销；完成后建议再跑一次安全检查。

### 匹配优先级与分类

| 分类 | 含义 | 处理 |
| --- | --- | --- |
| 未变化 | ID 相同且原文相同 | 可直接复用 |
| 可安全迁移 | 未变化且旧译文非空、新译文为空 | 默认迁移 |
| 原文相同但 ID 不同（建议） | 原文唯一一致、ID 不同 | 建议，需确认 |
| 存在匹配歧义 | 一条原文对应多个条目，或多个候选 | 不自动迁移，需人工确认 |
| 原文已修改 | ID 相同但原文改变 | 只显示旧译文作参考，**不**当作新版本译文 |
| 新增条目 | 新版本新增 | 需重新翻译 |
| 已删除旧条目 | 旧版本有、新版本无 | 只保留在报告中，**不**映射到其他条目 |

### 安全要求

* 迁移读取旧文件时只校验“是不是合法的 Toolkit Kit / JSONL”（`kind`、schema
  主版本、CSV 与 JSONL 一致），**不**要求与当前 Kit 同一 story——这正是跨版本
  迁移的前提；真正的对应关系由稳定 ID + 保护后原文决定，而不依赖 story 身份。
* 绝不用数组位置判断两个版本的对应关系。
* 不因为原文相似就覆盖已有新译文。
* 迁移前展示数量与预览，默认只向空白译文迁移。
* 迁移结果允许撤销，不会产生半完成状态。
* 迁移后建议执行安全检查。

## 三、实践建议

* 交接与迁移前后都导出“编辑工程 JSON”，方便随时恢复状态。
* 多人协作时约定由谁负责最终 `kit import` 与严格构建，避免重复导入。
* 迁移只做“确定安全”的部分；被标记为“原文已修改 / 匹配歧义”的条目请人工处理。
